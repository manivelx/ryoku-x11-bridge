# X11 lock security audit

Scope: `payload/bin/ryoku-x11-lock`, `payload/bin/ryoku-x11-suspend`, the overlay
in `scripts/apply-upstream-overlay.py` (lock dispatch, `spawnX11Locker`,
`isLocked`, lock recovery, power guard), the wrapper tests, and CI.
The audit originally started from `b06d4f9`; its fixes are integrated on `rxb/disposable-install-validation`.

This is independent software-level evidence. It is **not** target-hardware
acceptance and does not by itself make RXB installation-ready.

## Findings and fixes

| # | Finding | Fix |
|---|---------|-----|
| 1 | Lockers were resolved through `$PATH`; a user-writable PATH entry could supply a fake `xsecurelock`/`i3lock` that holds the lock file without locking the screen. | Lockers resolve only from the absolute `/usr/bin` (`locker_dir`); the Go side accepts the same directory only. |
| 2 | A repeated request reported success whenever the lock file was held, even with no live locker. | Success is reported only if a verified locker exists; otherwise exit 75. |
| 3 | Locker detection by `/proc` scan (exe/environ/fd) cannot work: XSecureLock sets `PR_SET_DUMPABLE 0`, so those entries are unreadable. | The wrapper records `<pid> <starttime>` for the display; verification checks `/proc/PID/stat` starttime (PID-reuse defence), state not zombie, real uid, `comm`, and `exe` when readable. The Go daemon (`x11LockerActive`) uses the same record. |
| 4 | `host:D.S` and `host:D` used different locks, allowing two lockers on one display. | Display names are normalised before keying lock and record. |
| 5 | A stray `WAYLAND_DISPLAY` inside an X11 session routed lock to the Wayland qylock path and suspend/hibernate to the Wayland path (hibernate without an X11 lock). | Session detection also honours `RYOKU_WM=i3` / `XDG_SESSION_TYPE=x11` in the lock wrapper, suspend wrapper, and the Go overlay (`rxbX11Session`). |
| 6 | The overlay's `isLocked` could report locked from weaker process evidence. | Replaced by the verified-record check above. |

Per-display `flock` on fd 9 is inherited by the locker, so it lives exactly as
long as the locker, even if the wrapper is SIGKILLed (tested).

X11 suspend and hibernate remain disabled and fail closed (exit 69). Nothing
enables them.

No path was found that shows a fake lock screen: RXB never draws its own lock
surface on X11; it only runs XSecureLock (PAM via its auth helper) or i3lock
(PAM). With neither installed it exits 127.

## Evidence

- `scripts/test-x11-lock-wrapper.sh` (mutation-checked): selection, PATH
  hijack refusal, forced X11/PAM auth modules, removal of user-supplied
  `XSECURELOCK_*` overrides, lock lifetime, idempotency, normalisation, no
  false success (including a renamed-binary spoof), forged/stale/PID-reuse/garbage records.
- `scripts/test-x11-suspend-wrapper.sh`: suspend/hibernate refusal, stray
  `WAYLAND_DISPLAY`.
- Go tests generated by the overlay for the verifier, key derivation, record
  requirement and session detection.
- `scripts/test-x11-lock-pam-xephyr.sh` via `.github/workflows/x11-lock-pam.yml`:
  in a disposable `archlinux:base-devel` container (guards: env flag,
  `/.dockerenv`, root, and a root-owned mode-0600
  `/run/rxb-pam-test-disposable` marker), on an isolated Xvfb/Xephyr pair,
  with a temporary user that has a real `pam_unix` password. The real wrapper
  and real lockers run:
  1. XSecureLock, default PAM service.
  2. XSecureLock with an isolated `/etc/pam.d/rxb-test-*` file (`pam_unix`).
  3. XSecureLock with a deny-all (`pam_deny`) stack: the correct password must
     NOT unlock (negative control proving PAM decides).
  4. i3lock fallback (XSecureLock removed).
  For each: screen covered, one locker, repeated request does not add a
  locker, wrong password stays locked, correct password unlocks (except 3),
  full cleanup. The host's PAM configuration is never touched; the test runs
  in a container with its own `/etc`.

## Residual risks and unverified items

- Same-user processes can kill the locker; inherent to X11 lockers.
- The wrapper clears all inherited `XSECURELOCK_*` variables and forces
  `XSECURELOCK_AUTH=auth_x11` plus `XSECURELOCK_AUTHPROTO=authproto_pam`. A
  custom `XSECURELOCK_PAM_SERVICE` is accepted only inside the guarded disposable
  PAM test container and only when its service file is root-owned and not
  group/other-writable; normal desktop sessions use XSecureLock's compiled-in
  PAM service.
- Process liveness is not proof the keyboard/pointer grabs are held.
- System-level suspend (logind, lid, power key) is outside RXB's control.
- The record is user-writable runtime state; the pid/starttime/uid/comm checks
  limit but cannot eliminate a same-user attacker who runs a real locker of
  their own.
- i3lock forks a helper under `--nofork`; the test counts independent lockers.
- Not verified: real hardware, a real X11 session with the full RXB shell, the
  Go ipc package on the pinned upstream beyond what CI shows, multi-seat.
